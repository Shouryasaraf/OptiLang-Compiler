# OptiLang Compiler

OptiLang is a compact, statically typed language and educational compiler. It shows tokens, an abstract syntax tree, scoped symbols, three-address code, a control-flow graph, optimization records, stack bytecode, a virtual-machine trace, and program output for the same source file.

The Phase 3 compiler adds assignments, `while` loops, typed functions, calls, and returns to the Phase 2 language. A bounded stack VM executes generated bytecode. The original AST interpreter and optimized AST interpreter act as execution references; the driver compares their outputs with the VM output on each successful run.

## Requirements

- Python 3.11 or newer
- No third-party runtime packages

## Quick start

From the repository root:

```bash
python -m pip install -e .
optilang examples/phase3.ol --html phase3-explorer.html
python -m unittest discover -s tests -v
```

The example prints `120`. Open `phase3-explorer.html` in a browser to switch between compiler stages. The generated file works offline and does not depend on a server.

If you do not want to install the package, set `PYTHONPATH=src` and run `python -m optilang examples/phase3.ol --html phase3-explorer.html` on Linux/macOS. In PowerShell use `$env:PYTHONPATH='src'; python -m optilang examples\phase3.ol --html phase3-explorer.html`.

## Implemented language

```text
let x: int = 2 + 3 * 4;
x = x + 1;
while (x < 20) { x = x + 1; }
if (x == 20) { print(x); } else { print(0); }

fn add(a: int, b: int): int { return a + b; }
print(add(3, 4));
```

Primitive types are `int`, `float`, `bool`, and `string`. Functions have typed parameters and one explicit return type. Functions must be declared at top level and every function must have an evident return path. A function may call another function before its declaration. Nested blocks have their own variable scopes. Integer division truncates toward zero; integer remainder follows the corresponding quotient. `&&` and `||` short circuit. Prints format Python Boolean values as `True` and `False`.

## Compiler stages

1. The lexer records token kind, text, line, and column.
2. The recursive-descent parser builds an AST with operator precedence.
3. Static analysis checks declarations, types, scopes, function calls, and return values.
4. TAC shows temporaries, labels, branches, calls, and returns. A CFG groups the displayed TAC into basic blocks.
5. Constant folding and selected safe algebraic identities rewrite the AST. The report records each change and its operator position. Both original and optimized TAC are displayed.
6. The bytecode compiler lowers the optimized AST to stack instructions. The VM has instruction and call-depth limits.
7. The driver compares original AST, optimized AST, and VM output. The visual explorer presents the results in one offline HTML file.

The TAC is an inspectable intermediate representation. This version lowers the optimized AST directly to bytecode; it does not use TAC as the executable backend input. The AST interpreter remains a reference engine for output comparison.

## Demonstration and limitations

See [docs/USER_GUIDE.md](docs/USER_GUIDE.md) for commands, language examples, expected output, and common errors. See [docs/PHASE3_REPORT.md](docs/PHASE3_REPORT.md) for architecture, evaluation and submission evidence.

SSA conversion, advanced data-flow and loop optimizations, native machine code, garbage collection, and formal proof of all optimizations are beyond this individual laboratory implementation. Differential execution checks observed outputs for the tested programs; it is not a formal equivalence proof.
